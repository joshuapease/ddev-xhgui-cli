# ddev-xhgui-cli 1.0 Release Plan

## Audit Summary (2026-07-06)

### How the add-on works today

The add-on is two files installed into a DDEV project plus a manifest:

1. **`install.yaml`** declares `commands/web/xhgui-query` and `xhgui-cli/query.php` as `project_files`, requires DDEV >= 1.24.4, and `chmod +x`'s the command after install.
2. **`commands/web/xhgui-query`** is a bash DDEV web command (runs *inside* the web container). It detects whether stdout is a TTY, exports `XHGUI_IS_TTY=0|1`, and `exec`s into PHP so PHP's exit code becomes the command's exit code (`ExecRaw: true` keeps DDEV from swallowing flags like `--help`).
3. **`xhgui-cli/query.php`** is a single-file, zero-dependency PHP tool. It connects to `mysql:host=db;dbname=xhgui` with the standard DDEV `db/db` credentials and serves two subcommands:
   - `runs` — reads only the denormalized columns (`id, url, main_wt, main_cpu, main_pmu, request_ts`), never the profile blob. Sorting goes through a hardcoded allowlist (`SORT_MAP_RUNS`), URL filtering through a parameterized `LIKE` with wildcard escaping.
   - `top-functions` — fetches one profile blob (with a `LENGTH()` pre-check and >20MB warning), gzip-detects by magic bytes, `json_decode`s it, then runs `computeExclusiveTimes()`: a single pass over XHProf's `caller==>callee` edge map that accumulates per-function inclusive totals and per-parent child sums, then computes `exclusive = inclusive − children`, flooring negatives at 0 (XHProf shared-callee limitation).

Output contract: table on TTY, JSON when piped (`--format` overrides); data on stdout, human messages on stderr; JSON errors get an `{"error": {code, message}}` envelope; exit codes 0/1/2/3 (success/usage/infra/data). Empty results are exit 0 with valid JSON.

### What's in good shape

- **Tests**: 109 PHP unit assertions across 4 files — all passing locally on PHP 8.4 (verified 2026-07-06). 8 bats integration tests covering install, both subcommands, JSON validity, filtering, error exit codes, and empty results.
- **CI**: unit job (PHP 8.1) + integration matrix (`ddev stable` and `HEAD`), daily scheduled run, tmate debug hook. Mirrors the official add-on template.
- **Security posture**: sort/format allowlists, parameterized queries with `EMULATE_PREPARES => false`, run-id regex, LIKE-wildcard escaping, terminal-escape sanitization in table output, no `unserialize()`. All seven constraints from the original plan doc are implemented.
- **Positioning is validated**: `ddev/ddev-xhgui` was archived 2025-04-07 because XHGui moved into DDEV core (v1.24.4+) — but core only ships a *web UI*. Nothing in core or the registry offers CLI/agent access to the profile data. The gap this tool fills is real and uncontested.

## What "1.0" means for this project

1.0 is a **stability promise, not a feature milestone**:

- **Frozen contracts**: JSON schemas, exit codes, flag names, and the `xhgui-query` command name don't break within 1.x. (This is why finding #7 must land *before* 1.0 — the arg-parsing surface is part of the contract.)
- **Clean lifecycle**: install, upgrade, and removal all verified by CI (finding #2).
- **Documented limits**: supported DDEV versions, database families, and PHP floor stated explicitly.
- Deferred features (`compare`, `export`, `--since`, aggregation) stay deferred — they're 1.x additions, not 1.0 blockers.
- **One feature addition is in 1.0 scope: the `callers` subcommand** (decided 2026-07-06; see Phase 4). It closes the one real gap in the headline agent loop, and it must land before 1.0 because it extends the CLI surface that 1.0 freezes.

Recommended release train: **v0.1.0 soft launch → v0.2.x hardening from feedback → v1.0.0 + announcement push.** Tagging 0.1.0 first gets the registry listing and real-world feedback before the contracts freeze.

### "How It Works" section outline

Written for a curious user, ~4 short subsections with one diagram:

- **The pipeline**: `ddev xhgui-query` → bash web command inside the web container → TTY detection via `XHGUI_IS_TTY` env var → `exec php query.php`. Why a web command: direct `db:3306` access with standard credentials, the project's own PHP runtime, no `ddev exec` overhead, and PHP exit codes pass through untouched (`ExecRaw`). A small ASCII/mermaid diagram: host CLI → web container → bash → PHP → MySQL `xhgui.results`.
- **Where the data lives**: DDEV's XHGui integration stores each request as a row in `xhgui.results` — denormalized totals (`main_wt`, `main_cpu`, `main_pmu`, `request_ts`) plus a `profile` LONGTEXT blob of XHProf's `caller==>callee` call-edge map. `runs` touches only the cheap columns; `top-functions` decodes one blob.
- **Exclusive time, explained**: XHProf reports *inclusive* metrics per call edge. The tool sums inclusive totals per function across all its callers, sums each function's direct-children costs, and subtracts: `exclusive = inclusive − children`. Negatives (a known XHProf artifact when a callee is shared by multiple callers) floor to 0 — same convention as the XHGui web UI. A 3-function worked example (`main() → foo() → bar()`) with real numbers makes this land in ~10 lines.
- **Output contract**: table for eyes, JSON for pipes; stdout is data, stderr is commentary; exit codes 0/1/2/3; errors in JSON mode still produce parseable stdout. Micro­seconds/bytes in JSON (no rounding), ms/MB in tables.

**Phase 1 exit criteria**: README renders well on GitHub *and* addons.ddev.com; every command/flag documented matches actual behavior (verify finding #6 while writing); a `CLAUDE.md` consumer snippet exists.

### 1.0 feature: `ddev xhgui-query callers`

**Why it's in 1.0**: closes the one real gap in the agent loop (per the Phase 1 gap analysis). When `top-functions` fingers an internal function like `PDO::query`, `{closure}`, or a vendor method, an agent can't grep its way to the userland culprit — it needs to ask "who calls this function, and how much of its cost comes through each caller?" The decoded `caller==>callee` edge map already contains the answer; today `computeExclusiveTimes()` parses and discards it.

**Proposed interface** (final flags to be confirmed during implementation):

```bash
ddev xhgui-query callers --function <name> [--run-id ID] [--sort wt|cpu|pmu] [--limit 10] [--format table|json]
```

- `--function` (required): exact function name as reported by `top-functions` (e.g. `PDO::query`)
- Same `--run-id` default (most recent run, stderr note), same TTY/JSON auto-detection, same exit codes; function not present in the run's profile → exit 3
- Output: one row per caller edge — caller name, call count, and the wt/cpu/pmu attributed to that edge, plus each edge's share of the callee's total (so an agent can say "82% of PDO::query time comes through ProductRepository::all")

**Implementation notes**:

- Refactor the edge-map walk so `computeExclusiveTimes()` and the new callers lookup share one pass/structure rather than re-decoding the blob
- The profile is per-run and already in memory when decoded — no new SQL beyond the existing blob fetch
- Consider the reverse direction (`callees`) only if it falls out for free; it's not needed for the loop and shouldn't delay 1.0

**Definition of done**: unit tests for the caller aggregation (multi-caller, single-caller, recursive edge, function absent), a bats test exercising `top-functions` → `callers` end-to-end, README updates (command reference + extend the "agent loop, end to end" example to show the `PDO::query` → `callers` → grep step + update the Known Limitations bullet that currently says there's no drill-down + update the CLAUDE.md consumer snippet), and JSON schema documented before the 1.0 freeze.

## Addendum (2026-07-06): agent-loop gap analysis from Phase 1

Phase 1 (README + How It Works) is complete. While writing it, the loop — generate traffic → query profiles → find the slow code in the source — was walked end-to-end against `query.php`'s actual behavior. Verdict: **the loop works today**; the gaps below are friction, not blockers. Resolutions are slotted into existing phases.

| Gap | Severity for the loop | Resolution |
|-----|----------------------|------------|
| No callers/callees drill-down: when `top-functions` fingers an internal leaf (`PDO::query`), an agent can't ask "who calls it" — even though the decoded `caller==>callee` edge map already has the answer | Friction, borderline loop-breaking on DB-heavy profiles | **Accepted into 1.0 scope (2026-07-06)**: `callers` subcommand, spec'd in Phase 4. README documents the grep-for-callers workaround until it ships |
| Correlating "the request I just made" with a run: `request_ts` is second-granularity, no `--since` flag, concurrent/asset requests can bury the target | Friction | README steers to `--url` filtering (done). Later: `--since <ts>` flag on `runs` — 1.x |
| Unknown flags silently ignored; `--limit=5` syntax silently dropped → agent gets defaults with no error | Friction (footgun) | Already Phase 2 finding #7; gap analysis confirms priority |
| Internal/unGreppable names (`PDO::query`, `{closure}`, `main()`) dead-end a naive grep | Friction | Resolved in README: documented as "signal about the kind of work; grep for the callers" |
| `ddev restart` disables profiling mid-session | Friction | Resolved in README (Quick start + Troubleshooting). Note: runs are NOT cleared on restart — the xhgui DB persists in the db volume; only the prepend-mode profiler loses runs on restart |
| `top-functions` JSON lacks run totals, so "this function is 60% of the request" needs a second `runs` call | Cosmetic | Add `total_wall_time_us` / `total_cpu_time_us` to the envelope — 1.x (additive, schema-compatible) |

Code/docs mismatches confirmed during the rewrite (all already tracked as findings #1, #7, #9): the `owner/` placeholder in the bash wrapper's error message, space-only flag syntax, and the un-pretty-printed empty-`runs` JSON. The README documents actual behavior in each case.

1. **Release cadence**: agree with the 0.1.0-soft-launch-first approach, or go straight to 1.0?
2. **PHP floor** (finding #5): document 7.1+, or spend 10 minutes to support 7.0? (5.6 support would mean rewriting nullable hints and testing — probably not worth it in 2026.)
3. **`--version` source of truth**: hardcoded const bumped at release time, or injected from git tag during release? (Const is simpler; there's no build step.)
4. **Marketing voice**: is Viget the publishing home for the launch post, or a personal blog?
5. **Official add-on ambition**: worth pursuing DDEV-official status eventually, or stay contrib?
